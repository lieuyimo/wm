## 0. 八个问题的直接回答

1. **A100 环境是否正常？** 正常。A100-SXM4-80GB，驱动 595.71.05，PyTorch 2.5.1+cu124，Python 3.11.15；4096×4096 CUDA 矩阵乘通过。GPU 0 空闲，GPU 2–5 被其他用户的 vLLM 占用，未触碰。
2. **训练了多少 Epoch、多久、多少显存？** 10/10 epoch，墙钟 60.41 s（epoch 内合计 48.34 s，约 4.83 s/epoch）；PyTorch 分配器峰值 65.8 MiB，整卡 `nvidia-smi` 峰值 633 MiB；1 s 采样 GPU 利用率均值 2.39%、峰值 4%。
3. **是否正常收敛？** 训练/验证损失单调下降，无 NaN/非有限损失；验证损失 0.4961→0.3021，最优 epoch 10。验证损失到第 10 轮仍在下降，属于“趋势正常但尚未完全收敛”，固定 10 epoch 上限截断了训练。
4. **比之前 CPU smoke 模型改善多少？** 在与 CPU smoke 相同的 200 条测试前缀协议下：Tartu 一步联合准确率 0.655→0.775（+12.0 个百分点），5 步 0.462→0.545（+8.3 个百分点）；clinic 一步 0.655→0.800（+14.5 个百分点），5 步 0.279→0.377（+9.8 个百分点）。规则基线数值未变，窗口数也完全一致（Tartu 5 步 156、clinic 5 步 122）。但训练数据规模/epoch 同时变化，不能把增益全部归因于 GPU。
5. **与修正规则模型相比差距多少？** 全量测试集：一步联合准确率 Tartu 0.7787 vs 0.9713（−19.26 个百分点），clinic 0.8031 vs 0.9333（−13.02 个百分点）；3 步 −26.95/−20.84 个百分点；5 步 −31.35/−24.30 个百分点。模型的服务完成精确率更高，但召回率更低；联合准确率的差距主要来自机器人位置。
6. **神经世界模型有没有实际改善调度？** 没有。16 个场景全部 6/6 完成，完成率 100%，无法区分策略；平均流转时间 `nearest` 75.864、修正规则 76.760、神经 77.344 步；神经比修正规则差 0.583 步（0 胜/4 负/12 平），比 `nearest` 差 1.48 步；工作站实际服务等待、最大积压、最大等待全部相同。模型推理 0 回退、0 离散安全违规，但不能据此声称调度改善。
7. **限制主要来自数据、模型还是目标设计？** 首要来自**数据**（故障训练覆盖极低、没有失败/超时 episode、车队和任务规模小）和**目标/评价对齐**（一步状态准确率不等于闭环流转时间）；**模型表达能力**是次要但真实的限制（均值池化集合网络没有成对关系，机器人移动过预测）；**训练**也有贡献（服务完成类别不平衡、无多步序列训练、10 epoch 上限）。
8. **下一步应该补故障数据、改集合网络，还是上 GNN？** 先补**故障训练/验证数据**，并把调度目标与评价对齐；同时做服务头校准和多步训练。只有在固定数据上确认关系信息是瓶颈后，再给现有集合网络加入成对关系特征或升级小 GNN；不建议现在直接扩大参数或上 Transformer。

|---|---:|---:|---:|
| train / short_outage | 2 / 24 | 10 | 5 |

| test_tartu / short_outage | 0 / 8 | 0 | 0 |
| test_clinic / short_outage | 8 / 8 | 52 | 10 |

短故障 episode 都有站点不可用（24/24、8/8、8/8、8/8），但多数故障没有与服务重叠。训练集 11,848 条转移中只有 10 个真实服务暂停 tick；验证集和 Tartu 测试集为 0。结论：当前训练数据**包含**故障样本，但覆盖极低，不能支撑故障泛化结论；clinic short_outage 的测试值只能作为该测试集上的观测。

### 2.4 划分与泄漏检查

- 按完整场景划分：训练/验证/同地图测试/跨地图测试的 seed 组和任务表均不重叠；validator 会拒绝跨 split 的 seed 或任务表重复。
- 未来信息：validator 检查 `release_tick <= tick`、下一观测 tick=当前+1、已知任务不消失、机器人移动在地图边上、站点静态映射不变、assignment 只引用当前 idle 机器人和 waiting 任务。
- 适配器输入只使用当前观测、当前 assignments 和静态地图；`next_observation` 只用于构造标签。`model.forward()` 不接收标签。
- 检查点绑定数据 manifest 哈希、适配器源码哈希和 8 个共享代码文件哈希；本轮重新拉取同一 commit 后逐项校验一致，评估入口不会绕过完整性检查。

## 4. 预测能力评价

评估使用固定检查点、同一批独立测试轨迹；测试集未用于训练或选 epoch。全量测试集为 3,904（Tartu）+ 1,529（clinic）条转移。

### 4.1 一步联合状态预测（全量测试集）

| split | 模型 | 联合准确率 | 机器人位置 | 任务状态 | 服务完成召回/精确率 |
|---|---|---:|---:|---:|---:|
| test_tartu | persistence | 0.0082 | 0.2408 | 0.9872 | 0 / — |
| test_tartu | 原规则 heuristic | 0.9713 | 1.0000 | 0.9947 | 0.6818 / 0.6818 |
| test_tartu | 修正规则 progress_rule | 0.9713 | 1.0000 | 0.9947 | 0.6818 / 0.6818 |
| test_tartu | **神经 learned** | **0.7787** | 0.8960 | 0.9964 | 0.6364 / 0.9032 |
| test_clinic | persistence | 0.0235 | 0.3241 | 0.9596 | 0 / — |
| test_clinic | 原规则 heuristic | 0.9294 | 0.9961 | 0.9854 | 0.7614 / 0.7053 |
| test_clinic | 修正规则 progress_rule | 0.9333 | 0.9961 | 0.9863 | 0.7727 / 0.7234 |
| test_clinic | **神经 learned** | **0.8031** | 0.9166 | 0.9888 | 0.6136 / 0.9391 |

要点：

- 神经模型的**任务状态准确率反而略高**（Tartu 0.9964 vs 0.9947；clinic 0.9888 vs 0.9863），服务完成精确率也更高；但服务完成召回率更低（漏报完成）。
- 联合准确率的差距主要来自**机器人位置**：Tartu 0.8960 vs 1.0000，clinic 0.9166 vs 0.9961。联合指标要求两个机器人及所有已知任务同时正确，少量移动错误就会让整个样本失败。
- 神经模型在 32 个测试 episode 中**没有任何一个**的一步联合准确率超过修正规则；最好的是 clinic seed 10003（0.881 vs 0.952），最差的是 Tartu seed 9003（0.692 vs 0.980）。

## 5. 调度闭环评价

### 5.1 设置

- 场景：2 张地图 × 4 个测试 seed × 2 个 regime（normal/short_outage）= 16 个场景，每个 6 个任务、2 个机器人。
- 策略：
  - `nearest`：传统最近距离基线；
  - `world`：现有预测世界模型基线；
  - `rule`：现有截止时间优先规则基线；
  - `progress_rule_rollout`：修正服务进度规则 + 外部 RolloutPolicy；
  - `neural_rollout`：神经世界模型 + 同一个外部 RolloutPolicy。
- 外部 RolloutPolicy：horizon=3，candidate budget=8，每次 dispatch 选 1 个 assignment。两个外部策略使用完全相同的候选顺序、外生事件、seed 和服务时长 key。
- 限制：`nearest/world/rule` 是 Simulator 原生策略，可能在同一 tick 分配多个兼容任务；外部 RolloutPolicy 每次只分配 1 个。因此“神经 vs 修正规则”是严格同预算配对；“神经 vs 原生基线”存在 dispatch 粒度差异，只作参考。
- 本批场景没有 deadline，`late_count` 不适用。

- 完成率全部 100%，不能用完成率证明任何策略更好。
- 工作站实际服务等待、最大积压、最大等待任务三项在 5 个策略中完全相同；没有任何证据表明世界模型减少了服务等待或异常后的资源积压。
- 神经模型与原生 `world/rule` 的聚合流转时间相同；修正规则略好于神经（0.583 步），但仍不如 `nearest`（1.48 步）。
- 神经模型 0 次 fallback、0 次离散安全违规；16 场景共约 513 次单步推理（32.06/场景），决策均值 6.6 ms、p95 17.4 ms。调用成功不等于调度改善。
- 结论：**当前神经世界模型没有实际改善调度**；修正规则也没有超过 `nearest`。本批场景太小、太容易，且没有 deadline/失败，可能是差异很小的原因之一。

## 6. 失败案例与原因分析

### 6.1 典型失败案例

- **最差**：Tartu seed 9003（normal/short_outage 都是 0.692 vs 规则 0.980）。机器人位置准确率 0.852；服务完成召回 0.636 vs 0.727。
- **第二差**：clinic seed 10002 normal（0.717 vs 0.943）。机器人位置 0.868；服务完成召回 0.636 vs 0.818。
- **最好**：clinic seed 10003 normal（0.881 vs 0.952）。机器人位置 0.970；服务完成召回 0.545 vs 0.818。
- 32 个 episode 中，神经模型 0 次超过规则、0 次持平、32 次落后；差距是系统性的，不是单个异常 episode。

### 6.2 证据：错在机器人移动，不在任务状态

全量测试集一步计数：

| 数据集 | 指标 | 神经 | 修正规则 |
|---|---:|---:|---:|
| Tartu | 机器人位置正确 | 6,996 / 7,808 (89.6%) | 7,808 / 7,808 (100%) |
| Tartu | 实际移动正确 | 5,848 / 5,928 (98.65%) | 5,928 / 5,928 (100%) |
| Tartu | 预测移动数 / 实际移动数 | 6,584 / 5,928（多 656，11.1%） | 5,928 / 5,928 |
| Tartu | 服务完成召回 / 精确率 | 0.636 / 0.903 | 0.682 / 0.682 |
| Tartu | 服务完成预测数 / 实际数 | 124 / 176 | 176 / 176 |
| clinic | 机器人位置正确 | 2,803 / 3,058 (91.7%) | 3,046 / 3,058 (99.6%) |
| clinic | 实际移动正确 | 1,925 / 2,067 (93.1%) | 2,061 / 2,067 (99.7%) |
| clinic | 预测移动数 / 实际移动数 | 2,155 / 2,067（多 88，4.3%） | 2,069 / 2,067 |
| clinic | 服务完成召回 / 精确率 | 0.614 / 0.939 | 0.773 / 0.723 |
| clinic | 服务完成预测数 / 实际数 | 115 / 176 | 188 / 176 |

- 机器人移动**过预测**：Tartu 多预测 656 次移动，clinic 多 88 次；模型倾向于在机器人实际被阻挡/等待时预测移动，或选错相邻格。
- 服务完成**欠预测**：Tartu 少预测 52 次完成，clinic 少 61 次；精确率高、召回低，符合类别不平衡下的保守阈值。
- 任务状态准确率略高，但联合指标被机器人位置拖累；修复移动头比修复服务头对联合准确率更关键。

### 6.3 四类原因

**A. 数据问题（首要）**

- 训练集 11,848 条转移只有 10 个真实服务暂停 tick；验证集/Tartu 测试集为 0；clinic short_outage 有 52 个暂停 tick，但训练集没有 clinic。模型无法学习“故障导致服务等待”的动力学。
- 96 个 episode 全部 6/6 完成，没有失败/超时 episode；场景只有 2 个机器人、6 个任务、无 deadline。数据缺少调度真正困难的拥挤、争用、故障积压和任务失败样本。
- 机器人数量固定 2，无法评价多机器人泛化。

**B. 模型表达能力（次要但真实）**

- 4,642 参数、26 维实体 token、32 维隐藏层；实体编码后做掩码均值池化，形成全局上下文。均值池化是顺序无关的，但**没有成对关系**：无法显式表达“机器人 A 挡住机器人 B”“任务 T 与机器人 R/站点 S 的匹配”“候选分配之间的冲突”。
- 运动候选特征包含局部路径和其他机器人位置，但全局上下文丢失实体身份；机器人移动过预测/选错相邻格与缺少成对占用推理一致。
- 这不能单独解释全部差距（模型仍学到 0.78/0.80 的一步联合准确率），但它是下一步最值得验证的结构限制。

**C. 训练问题（可修复）**

- 验证损失到第 10 轮仍在下降（0.3041→0.3021），10 epoch 上限可能截断收敛；A100 利用率仅 2.39%，延长训练的成本很低，但不应在未修数据/目标前盲目扩大。
- 服务完成是严重类别不平衡：Tartu 176 次完成 / 21,296 个任务实例（0.83%），clinic 176 / 6,726（2.62%）；BCE 未做类别加权/阈值校准，导致召回低。
- 只训练单步转移，没有 3/5 步序列窗口或 scheduled sampling；多步递归误差累积（5 步联合降到 0.585/0.485）与这一训练设置一致。
- 未观察到 NaN/梯度异常；训练稳定性不是问题。

**D. 预测目标与调度评价脱节（闭环结论的首要解释）**

- 训练目标是单步运动分类 + 服务完成 BCE；闭环评价是任务流转时间/等待/积压。两者没有直接优化关系。
- 闭环中 `nearest` 平均流转 75.864 步，反而优于 `world/rule` 77.344 和神经 77.344；说明在这些场景里，预测辅助的分配评分没有带来收益，甚至不如最短路径。
- 神经模型与原生 `world/rule` 聚合结果相同，修正规则略好但仍不如 `nearest`；工作站等待/积压完全不变。模型调用成功、fallback=0、安全违规=0，但这些都不等于调度改善。
- 现有 RolloutPolicy 的评分是“预测终态到目标的距离”，不是长期流转时间；预测误差与评分误差可能相互抵消或放大，目标需要重新设计/对齐。

## 7. 下一步建议（按优先级）

### 7.0 为什么本 PR 不改模型/训练代码

本轮的目标是先建立可复现的 A100 基线。协议明确要求：不直接扩大网络、不改变预测目标、不进行大规模超参数搜索、优先复用现有训练框架，并且不能用测试集调参。若在同一 PR 中改模型、损失或数据生成，就无法区分“GPU 训练验收是否通过”和“改进是否有效”，也会把基线差距与改进效果混在一起。因此本 PR 只提交基线报告与精简证据；模型/训练改动应作为独立 PR，在固定数据和固定评价协议下做对照。

### 7.1 当前困境（需要 reviewer/导师决策）

1. 预测仍明显落后修正规则：全量测试一步 −19.26/−13.02 个百分点，5 步 −31.35/−24.30；32 个测试 episode 中神经模型 0 次超过规则。
2. 闭环没有改善：16 个场景全部 6/6 完成；平均流转 `nearest` 75.864 < 修正规则 76.760 < 神经 77.344；工作站等待、最大积压、最大等待完全相同；神经对修正规则 0 胜/4 负/12 平。
3. 故障训练覆盖几乎为零：11,848 条训练转移只有 10 个真实服务暂停 tick；验证集/Tartu 测试集为 0。不能宣称故障泛化。
4. 主要错误在机器人移动而不是任务状态：移动过预测（Tartu +656、clinic +88），服务完成欠预测（召回 0.61–0.64）；联合指标被机器人位置拖累。
5. 目标与调度脱节：一步状态准确率不是流转时间；现有 RolloutPolicy 评分没有带来收益。

下一步不是“改代码就完事”，而是需要先决定投入顺序：A 数据优先（推荐）、B 训练优先（服务头校准 + 多步训练）、C 结构升级（关系特征/小 GNN）、D 目标重构（决策价值/长期流转）。本 PR 不包含以上改动；若同意，建议下一个 PR 先做 A+B 的最小组合，并保持同一套评估/闭环协议。

### 7.2 按优先级的建议

1. **先补故障数据（A）**：构造故障确实与服务重叠、产生等待/积压/失败的训练和验证 episode；保持按场景/seed/任务表分组隔离；固定数据后再比较模型。当前数据无法区分“模型不会”与“数据没教”。
2. **服务头校准与类别加权（C）**：在验证集上做 class weight 或阈值校准，报告召回/精确率；不要用测试集调阈值。目标是把服务完成召回从 0.61–0.64 提到规则水平，同时保持精确率。
3. **多步训练（C）**：加入 3–5 步展开、scheduled sampling 或多步损失，直接优化多步一致性；当前 5 步衰减（−31.8 个百分点 clinic）主要来自单步训练的递归误差。
4. **关系特征/小 GNN（B）**：在固定数据上先加入成对机器人-机器人、机器人-任务-站点关系特征，验证移动头是否改善；若仍不足，再升级为小 GNN/注意力。不要直接上 Transformer 或盲目扩大参数。
5. **目标对齐（D）**：用决策价值/长期流转目标训练或重排候选，而不是只用一步状态准确率；复用现有 `long_score_experiment` 的固定协议，在独立确认集上预注册评价。当前闭环已经证明“预测更准”不等于“调度更好”。
6. **延长训练（低成本）**：A100 利用率仅 2.39%，10 epoch 只用 60 s；在数据和目标修正后，可把 epoch 上限提高并仍按验证集选检查点。单独延长训练不太可能弥补 13–19 个百分点的规则差距，但可作为消融。
7. **论文表述**：把本轮定位为“GPU 工程验收 + 当前模型的诚实负结果”；不要把 100% 完成率、0 fallback 或训练成功解释为世界模型改善调度。修正规则仍是强基线，`nearest` 在本批场景仍是最好流转时间。
