# PR42：冻结 V4 的动作关系可识别性审计

**性质：机制诊断，不是新调度策略或新模型性能声明。** 本分支基于 PR40 已有 V4-H20 源代码，不修改 V4 权重、PR39/40/41、原网络、CP-SAT 或业务状态规则。

## 研究问题

不同的合法机器人-任务-工作站关系，在数值编码中是否能够区分？在两个候选真实结局不同的情况下，V4-H20 是否给出不同的未来系统状态预测？

PR39 的 assignment-specific 与合成健康信号结果来自其离线候选重排。992 条完整记录与分析脚本未提交，不可将它们声称为本轮已取得的可复现原始数据。本轮明确复用已公开的 PR30 场景和 PR29 实验函数。

## 冻结方法

- 使用 PR30 **已使用过**的 8 个合成场景，每种负载 light/medium/heavy/shift 两组。仅为开发集机制诊断，不是独立泛化验证。
- 对同一个 tick 0 公开观测状态，取原生 CP-SAT 前两个不同的合法方案。每个方案由原 BusinessSimulator 独立执行首步，之后使用相同 CP-SAT 策略和 keyed random 机制。真实事实仅用于**离线评价**。
- 对每个候选，调用现有公开状态特征生成函数，分别记录机器人-样本-取样站-交付站链接、实际 encode_tokens 产生的数值 token 多重集、原始 Deep Sets 的实体均值池化结果、合格的已启动服务查询。
- 用同一个冻结 V4 权重和现有 forecast_pair 执行 H20/P3 滚动预测，记录完成、等待、运输和资源占用的未来预测，并与真实 tick 20 的可观测业务状态对比。真实轨迹如果已经结束，tick 20 状态记为缺失，不虚构数值。
- 记录每个候选真实 makespan、逾期、等待、安全结果；**真实结局绝不作为模型预测、候选评分或输入特征**。
- 全程 0 GPU、0 新训练、0 新网络、0 修改规则、0 使用未来故障 oracle，不推断真实设备预兆的可获得性。

## 结果解释边界

1. 不同关系具有完全一致的数值 token 多重集，只能证明该输入对在当前编码下发生碰撞，不证明所有真实候选都会发生。
2. 池化表示很接近，只说明当前权重与状态下的敏感度低，不自动证明 Deep Sets 理论上无法建模。
3. 混合世界模型包含动作相关的确定性状态转移，因此神经网络信息碰撞不必然导致 H20 结果相同。
4. H20 预测打平和真实完成时间有差异，也不能直接归因于编码；候选续调度、粒子预算、评分对象都可能是原因。
5. PR30 场景已经被使用过，本轮不能宣称是独立测试或新地图泛化证据。

## 后续分流

- 若真实结果敏感的候选确实出现编码碰撞或 H20 评分打平：先测试**只修改输入编码**的关系保持基线，再判断是否需要消息传递网络。
- 若编码能区分候选但 H20 仍然失败：优先审查 continuation policy、任务层面的预测目标、粒子和评分函数。
- 若关系与未来状态均有区分能力但决策方向错误：优先研究模型校准和长期目标，而不是预设 GNN 必然有效。
- 新地图、设备健康条件与独立在线验证必须单独预注册、执行和评估；本轮不晋升默认生产模型。

### 本轮方法判断

**现有 V4 在这 8 组输入中没有观测到真实编码碰撞，也没有观测到 H20 多字段预测信息完全消失。** 最直接的线索是：当前决策评分只使用 H20 的预计完成工序数，而 shift 条件下完整 H20 状态摘要虽有差异，评分却退化为并列。

下一阶段应首先独立审计 *预测信息 → 决策评分* 的信息损失：使用相同冻结预测结果，分别比较完成数、等待状态、任务状态、资源占用等指标能否为 shift 候选增加有用的区分度，并在未使用的新场景中检验。**不得根据这 8 组反向调权重或把离线候选后悔值冒充在线收益。** 图关系编码与设备健康动态仍是待验证的方向，本轮证据不足以优先启动 GNN 训练。
