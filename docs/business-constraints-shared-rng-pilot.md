# 历史记录：策略与环境共用随机种子的试验

**该报告保留供审计，不再作为最终独立确认结果。** 复核发现，策略随机流与外生环境共用种子；代码没有使用该种子读取真实未来，但为了严格隔离信息来源，后续已分离策略/环境随机数并采用新确认种子。以下是修复前原报告的原始结果，数据未覆盖；修订后的实验协议见 [business-constraints-protocol.md](business-constraints-protocol.md)。

本轮从 PR #11 的 `0f7629b545de8abca0aad1ad2d36d9f066cbd006` 开始，扩展现有 CP-SAT 调度与执行适配；保留 PETS、进度感知规则和结构化服务头，不训练新网络。结果为合成场景上的工程验证，不代表真实实验室性能。实验前固定的规则、场景、预算、抽样及确认集重选原因见[实验协议](business-constraints-protocol.md)，机器可读数据和执行日志见[证据目录](../examples/evidence/business-capacity-20261109/README.md)。

## 业务规则及系统接口

- [场景编译](../business_transport/scenario.py)要求每个物理站点明确配置资源组与容量；同一资源组可以有多个物理服务点，容量不超过点位数。业务任务由配置提供连续的取送阶段，后一段只在前一段完成后释放；无配置或不连续路线会报错。单次取送继续兼容原接口。
- [BusinessCPSAT](../business_transport/dispatch.py)延续 PR #11 固定的 OR-Tools `9.14.6206`，使用官方 `CpModel`、可选区间、`AddNoOverlap`、`AddCumulative`、前后依赖和 makespan；实际距离继续调用 `Geometry.distance()`。当前已释放任务、空闲机器人、可见站点状态和公开流程模板在同一模型中协调。一个规划假设是该任务余下的阶段由当前机器人执行；实际每段完成后重新分配，求解器只提交本轮合法 `Assignment`。
- 设备当前不可用时只做一步占用估计，并不读取故障恢复时间；已经开始服务的资源占用依据可观察有效进度和历史服务均值估计，不读取隐藏剩余倒计时。资源占用直到服务结束，故障暂停时继续占位。后续未释放任务和未来故障不进入调度器或在线模型。
- [执行适配](../business_transport/simulation.py)由现有 `Simulator` 执行网格路径、碰撞检查和服务，只扩展服务准入及下一阶段释放；[容量感知转移](../business_transport/dynamics.py)对现有三种 `predict_next` 增加资源准入。世界模型递推仍只包含已释放阶段，尚不能预测下一阶段随后释放；它没有被包装成具备这种能力。
- 每次 CP-SAT 枚举最多 4 个分配计划，单线程，每次求解最多 0.5 秒墙钟、0.05 确定性时间；无解、超时或预测异常时采用已有合法候选，日志记录原因。对尚不具备业务规则的旧调用直接调用 PR #11 原实现。资源组容量不同于站点物理格占用，也不伪装成 FIFO 队列。

指定来源及许可未改变：Zhou 等论文 DOI [10.1039/D4DD00313F](https://doi.org/10.1039/D4DD00313F)作为业务参考；Google 官方 [flexible_job_shop_sat.py](https://github.com/google/or-tools/blob/100f66e6242ab8bf8d32feb8f3bf086db66ae2b5/examples/python/flexible_job_shop_sat.py) 固定源码 `100f66e6242ab8bf8d32feb8f3bf086db66ae2b5`，Apache-2.0。PETS 保留 MBRL-Lib 源码 `3f93cccfc8d635f74e335a2f07aab6e9a48fc021` 和已有权重，不改写其集成网络。原始源码复现、精确依赖及许可证详见[PR #11 集成报告](paper_reuse_integration.md)。

两张地图是 Moving AI MAPF 的通用网格基准，固定 LaCAM3 镜像提交 `1c3ecf8ade40298f16047544634e9c0c1cf3b93c`，并校验原始文件哈希；**并非真实实验室平面图**。所有站点位置、任务路线、服务时间、资源共享、容量和故障时刻是[场景文件](../business_transport/scenarios/benchmark.json)中的显式仿真假设。设备参数与流程尚需实际业务方提供或核对。

## 确认集与公平性

开发集为两张地图、各 1 个种子和 4 种工况；独立确认集为两张地图、各 2 个新种子、4 种工况，共 **16 个完整场景**。工况包括单段兼容、多阶段容量 1、多阶段容量 2 和多阶段设备中断。每场景 3 台机器人、6 个业务样本；多阶段样本按首段释放到末段完成计算一次流转。配置、任务、容量和持续时间冻结后运行，各组共用场景和外生扰动。测试无真实截止时限，超时数不适用；所有样本均在 500 仿真步限内完成。

A 是最近优先；B 是最近匹配候选加规则 Rollout；C、D、E 分别是 CP-SAT 候选加规则、PETS 混合和结构化服务头/规则移动混合。B–E 均评估至多 4 个候选、3 个粒子、5 步，使用相同 PR #10 工作量评分，候选后续模拟均调用最近优先。**B 以距离生成候选，C–E 以 CP-SAT 生成候选，因此不保证候选集合相同**；同状态诊断另行记录候选集合。A 不进行多候选预测，计算预算自然较小。

各场景机器可读记录包含样本结果、占用峰值、各候选预测与选择、求解状态、回退和完整墙钟时间序列。故障工况的资源等待与设备不可用等待被分别记录，不能把正常容量排队全当故障造成的延迟。

## 完整调度对照

下表为确认集每组 **96 个业务样本**、16 个场景的真实执行结果。流转、等待和占用的单位为仿真步；等待是各阶段从释放到分配的时间之和，容量等待和资源占用为所有场景合计。决策时间是本地 CPU 上从策略接收候选到返回分配的实际墙钟时间，均值和 P95 对全部决策计算，不包含仿真器预先生成合法候选的时间；数值依机器负载变化。

| 组别 | 完成 | 平均流转 | 每样本阶段等待 | 容量等待合计 | 资源占用合计（槽位·步） | 决策均值 / P95（ms） |
|---|---:|---:|---:|---:|---:|---:|
| A 最近优先 | 96/96 | 41.885 | 11.438 | 131 | 867 | 0.150 / 0.651 |
| B 最近优先 + 规则 Rollout | 96/96 | 42.469 | 12.875 | 102 | 855 | 14.910 / 24.746 |
| C CP-SAT + 规则 | 96/96 | 41.760 | 12.583 | 71 | 855 | 23.667 / 43.439 |
| D CP-SAT + PETS | 96/96 | 42.615 | 13.292 | 81 | 855 | 30.614 / 54.754 |
| E CP-SAT + 结构化服务头 | 96/96 | 42.458 | 13.115 | 78 | 855 | 44.030 / 72.042 |

确认集中三组 CP-SAT 调用分别为 C **126/126**、D **126/126**、E **127/127** 成功，求解和模型回退均为 0，候选未被超时截断；超容量、重复分配、非法生命周期及离散安全违规均为 0。每组 4 个容量 2 场景均观察到资源池同时服务 2 个样本。以 C 为例，4 个故障场景有 35 个站点不可用等待步和 41 个容量等待步；这些口径可能互相影响，不能直接相加解释为故障损失。

D 的 PETS 在闭环中实际执行 **3,899 次前向调用**，E 的结构化服务头执行 **3,954 次调用**。与 C 比较，D 的平均决策延迟增加约 **6.95 ms**，平均流转增加 **0.854 仿真步**；不是性能改进。C 相比 A 的平均流转差为 **−0.125 步**。按完整场景配对，D 相对 C 为 1 场景更好、5 更差、10 相同；地图/种子簇 bootstrap 的探索性 95% 区间为 [−0.083, 1.792] 步。只有 4 个独立地图/种子簇，不能把区间解释成可靠的泛化结论。

## 同状态动作与预测准确度

预先规定的 32 个普通/故障附近同状态决策点中，PETS 和结构化服务头相对规则的选择均为 **0/32 不同**；同样状态下最近候选和 CP-SAT 候选的集合交集/并集为 **118/118**。每个候选使用同一初始状态、同一外生扰动独立重放，其后均由最近优先执行；这些不是全局最优参考。

为了定位完整闭环出现不同动作的原因，在确认结果可见后额外检查四种来源策略轨迹中所有至少有两个合法分配候选的状态。此诊断有 **370 条相关决策记录**；按完整可观察状态去重为 **181 个状态**。其中 PETS 相对规则有 **21 次**选择不同：在固定最近优先后续策略的反事实重放中，5 次平均完整流转更好、15 次更差、1 次相同；结构化头有 20 次不同，4 好、15 差、1 相同。它们是**事后探索性诊断**，这些决策点彼此相关，不能当成 181 次独立实验或确认性的显著性证据。该诊断同状态下最近/CP 候选交集/并集为 1197/1215。

相同最近优先事实轨迹的已知实体联合状态准确率如下：先求每场景比例，再求场景平均；结果只覆盖每 5 个合格窗口中抽取的一个，并排除预测窗口内新任务/阶段释放、新分配或设备/容量可用性变化。它们不是所有故障时段的总体准确率。

本组没有显示学习模型优于规则或改善完整调度；多步预测误差更大。候选评分、模型、数据和时间窗口均未根据确认集结果调整，本轮也没有新训练或更换世界模型。

## 已知边界与失败记录

最初试验在 Tartu 和 clinic 医院公开地图上增加第三台机器人后，两张图均在 **800 步**时只完成 **4/9 个阶段**：拥堵恢复未产生有效计划，日志中阻塞持续出现。现有模拟器的联合恢复只覆盖两台机器人，不能据此声称三机器人在任意地图均可完成；此记录保存在证据目录，不能用新通过的通用地图掩盖。没有重新实现路径规划器。要用于更复杂真实布局，下一步必须为三台及以上机器人验证拥堵恢复和活性。

首次开发版把单位置 C 站容量隐式设为 1，违反全部容量明确配置的要求；这一版的配置和完整结果保留但不作为独立确认。修复后，确认种子在再次看结果前按任务表唯一性更换；原有场景和结果没有覆盖。[配置审计](../experiments/business_constraints/benchmark.py)检查开发、旧试验及新确认的任务表，以及与 PR #8–#11 来源地图哈希的重合。新公开通用地图和旧医院地图不是同一文件，但不能因此声称覆盖所有此前可能使用的业务分布。

## 复现和验证

以下命令使用 Python 3.10、固定 CPU 依赖；输出目录必须不存在或为空，防止覆盖历史结果。`run_cpu.sh` 将开发集与确认集各运行两次，比较除实测耗时外所有结果；补充诊断也独立重跑并逐字节比较。它复用仓库现有权重，不执行模型训练。

```bash
uv venv --python 3.10 .venv-paper
uv pip install --python .venv-paper/bin/python --index-strategy unsafe-best-match -r requirements-paper-reuse.lock
source .venv-paper/bin/activate
python -m unittest discover -s tests -v
python -m unittest discover -s experiments/service_value/tests -v
python -m unittest discover -s experiments/paper_reuse/tests -v
python -m unittest discover -s experiments/business_constraints/tests -v
bash tools/business_constraints/run_cpu.sh /tmp/wm-business-new-output
```

本地分别通过 **112、11、11、13 项**测试；功能包括单段兼容、配置校验、两/三阶段依赖、容量 1 排队与容量 2 并行、CP-SAT 资源区间、三种模型的容量转移、隐藏未来信息隔离，以及违规检测。独立 GitHub Actions 工作流见 [business-constraints.yml](../.github/workflows/business-constraints.yml)，它校验历史和本轮文件哈希，在标准 CPU runner 上运行回归及复现实验并保存工件。
