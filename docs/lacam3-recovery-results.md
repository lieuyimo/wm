# 官方 LaCAM3 联合路径恢复：实现与 CPU 验收

## 结论和范围

在 PR #13 的**原始 clinic 配置**中，PIBT 在 800 步内完成 2/5 项任务、4/9 个阶段；保留多步完整联合方案的混合后端在 115 步完成 5/5 项、9/9 阶段。两个后端使用相同的最近优先分配、任务表、设备状态和服务规则。这里只能说明该固定失败案例得到恢复；两张医院地图和 20 个通用场景不足以证明普遍活性，也不是独立的真实医院数据。

原 PR #13 冻结轨迹第 37 步后没有新的阶段完成，最后 100 步反复出现三个联合位置。clinic 的双向图有 62 个节点、25 个无向投影割点；多机器人朝重复目标行进时，逐步规划重复选择，出现可移动但业务不进展的循环。PR #13 对原阻塞状态已找到 5 步合法联合解围见证，因此不能将该案例简单归因于地图完全无路。两个机器人可能争用同一业务目标；原 PIBT 适配器每步新建求解状态，不跨步持久化优先级。这些现象支持“局部动作不断抵消且共享目标竞争”的诊断，不能单凭一个案例证明唯一根因。

先从 PR #13 归档中提取首次进入循环的状态、三个典型循环状态和原后端最终状态。五个输入均调用固定版本的作者 `solve()`，分别得到 5–6 步完整合法联合方案，才继续集成。[原始输入和全路径](../examples/evidence/lacam3-recovery-20261109/clinic-gate.json)包含每个机器人位置、业务目标、任务、阶段与锁定。

## 官方代码和适配边界

- 论文：[Engineering LaCAM*: Towards Real-Time, Large-Scale, and Near-Optimal Multi-Agent Pathfinding](https://www.ifaamas.org/Proceedings/aamas2024/pdfs/p1501.pdf)，AAMAS 2024。
- 作者代码：[Kei18/lacam3](https://github.com/Kei18/lacam3)，固定提交 `1c3ecf8ade40298f16047544634e9c0c1cf3b93c`；`third_party/argparse` 为 `69dabd88a8e6680b1a1a18397eb3e165e4019ce6`。两者均为 MIT，许可分别存于 [LaCAM3](licenses/lacam3-MIT.txt) 和 [argparse](licenses/argparse-MIT.txt)。未修改上游文件。
- 原样按 README 构建，官方 6 项 `ctest` 全通过；README 的 300 机器人示例 `solved=1`。构建、测试、示例的完整日志和结果存于[证据目录](../examples/evidence/lacam3-recovery-20261109/)。官方示例和本项目适配均使用 CPU。
- [C++ 薄桥](../native/lacam3_bridge/lacam3_worker.cpp)构造上游 `Graph`、`Instance` 并直接调用官方 `solve()`；核心联合搜索没有复制或重写。实验固定使用官方 `FLG_STAR=false`、单线程、无 refiner，取得**第一个完整方案**，不声称该方案最优。官方 PIBT 和原后端继续保留。
- [Python 适配](../business_transport/lacam3_motion.py)只接受双向图；锁定机器人顶点被排除，得到的整个路径再次检查合法边、顶点不重叠、禁止交换边和固定机器人不动。重复业务目标时按固定优先级保留一个真实目标，其余可动机器人临时目标为当前格、允许中途让路；这不改变真实任务。若临时目标仍冲突、目标锁住、图不支持或无完整方案，则记录并回退，不改道路规则。

混合策略在连续 16 步没有阶段完成、且最近联合位置重复时启动；正常进行中的服务不会单独触发。每次求解包含输入映射、子进程和路径校验在内，预算为 500 ms；同一业务目标与锁定集合只尝试一次，目标或锁定变化才允许再次求解。成功后缓存完整路径；新任务、任务阶段、设备/服务/锁定状态或实际位置与缓存不符时检查并失效。上述设置及不利结果均由[冻结协议](lacam3-recovery-protocol.md)和日志保留。

## 配对执行结果

下表括号内为完成阶段数；“受限平均流转”包含未完成任务，将其在运行截止时的已等待时间记入平均，因此适合观察截断结果，但并不等于全部任务最终完成后的真实平均流转时间。表中 800 是运行上限；表内完整场景均保持 PR #13 的任务、资源和扰动设置。

| 场景 | 原后端 | PIBT | PIBT + LaCAM3 |
|---|---:|---:|---:|
| Tartu，3 台 | 2/5（4/9），800 步；受限流转 527.2 | 5/5（9/9），175 步；113.0 | 5/5（9/9），175 步；113.0 |
| clinic，3 台 | 2/5（4/9），800 步；501.8 | 2/5（4/9），800 步；487.2 | 5/5（9/9），115 步；62.8 |
| 16 个通用场景，3 台 | 96/96（135/135） | 96/96（135/135） | 96/96（135/135） |
| 4 个通用场景，5 台 | 24/24（30/30） | 24/24（30/30） | 24/24（30/30） |

clinic 的最后阶段完成时刻分别为原后端 79、PIBT 37、混合后端 115；最长连续无阶段进展分别为 721、763、22 步。按“16 步窗口内出现过相同联合位置，且中间出现过不同位置”统计的重复**访问次数**分别为 22、751、22；这不是互不重叠的循环次数。PIBT 的 751 次表明机器人在移动，但该固定案例没有继续完成任务。

clinic 混合后端两次触发、两次实际调用官方求解器、两次成功，路径均为 6 步；第一条实际执行 5/6 步后因业务上下文变化失效，第二条执行 6/6 步。一次属于之后的新输入重新规划。所有计划及逐步执行、失效和计算耗时在压缩原始结果中。额外事后机制对照保持求解与触发条件相同，改为**只执行计划第一步并丢弃剩余缓存**，在 800 步仅完成 2/5；这支持在此案例中持续执行多步计划具有作用，但该消融是看到初步结果后追加的诊断，不是独立确认或普遍因果定理。

Tartu 原图存在 50 条无反向边的有向边，LaCAM3 适配器明确标记不支持，未改成无向图。混合后端在该案例没有调用 LaCAM3，结果来自 PIBT；不能把 Tartu 完成归功于 LaCAM3。16 个三机器人通用场景有 4 次因目标格被锁定而在调用求解器前安全回退；五机器人通用场景没有触发。三后端全部 66 次运行中，顶点碰撞、交换边、非法有向边、穿越锁定格、超容量、重复分配和非法生命周期均为 0；此为离散仿真检查，不代表真实机器人安全认证。

## 耗时和资源

同一台 CPU 环境的首轮结果：clinic 两次实际 LaCAM3 调用平均 **3.40 ms**、P95 **3.94 ms**、总墙钟 **6.80 ms**，两次求解器子进程 CPU 共 **5.27 ms**，最大单个求解器进程峰值 RSS **2,156 KiB**。只有两次调用，P95 不稳定。Python 主进程测得的是运行至当前场景的累计峰值，clinic 约 **282,484 KiB**；它包含 Python、PyTorch 和先前场景，不能与子进程峰值相加后冒充单场景独立内存。超时进程无法回传其内部 CPU/RSS 时，对应字段明确为空。

另对全部 66 次场景运行进行独立资源采样复跑，结果与配对记录中的任务数、阶段数和结束步数一致。以 20 ms 间隔采样进程树，clinic 混合后端最高采样区间平均 CPU 利用率为 **96.8%（以单核心为 100%）**，最高采样进程 RSS 之和为 **255.9 MiB**；逐场景数据在 `resource-profile.json`。这不是精确的瞬时峰值：短命求解器可能在两次采样之间退出，内核计时粒度及进程退出也可能使 CPU 区间估计偏高或偏低；进程间共享内存可能重复计入 RSS。该独立复跑的采样不影响上文配对实验中的延迟记录。

对 16 个三机器人通用场景，按场景平均再平均，运动步骤平均实际墙钟分别为原后端 **0.166 ms**、PIBT **0.850 ms**、混合 **1.052 ms**；对 4 个五机器人场景分别为 **0.268 / 1.473 / 1.317 ms**。这些是每个完整场景的均值再取平均，不能当作整体 P95；逐场景平均、P95 和全部逐步时间均在结果中。三机器人场景的平均任务受限流转分别为 **40.67 / 43.91 / 43.91 步**，五机器人为 **31.13 / 34.33 / 34.33 步**。PIBT 需要每步重建求解输入、距离信息和优先次序，且实际路径可能不同；这些设计会增加工作量，但本轮没有做 CPU 火焰图，不能量化各因素的因果占比。混合控制器也有观测与缓存检查开销，即使未真正调用 LaCAM3，低负载性能也并非完全零成本。

## 世界模型和执行器的接口一致性

恢复检测历史、缓存路径、有效条件和已尝试输入放进不可变 `RecoverySnapshot`；每个 Rollout 分支使用独立快照，不会写入实际执行器或其他分支。当前状态、静态图和可观察的服务/暂停状态是输入，未来任务、故障计划与隐藏服务倒计时不作为输入。预测服务状态有误时，后续缓存上下文也可以合理地与事实不同，不能把计划本身当作真实未来。

对 clinic 的 115 个事实一步转移，规则、PETS 和原结构化服务头各有 **115/115** 次机器人联合位置一致；紧接首次恢复方案的 4 步缓存递归预测均一致，实际第 57 步服务上下文变化导致缓存失效。服务状态相同条件下，恢复快照也分别一致 **112/112、97/97、107/107**；PETS 在全部事实一步中仅有 **107/115** 次快照一致，说明其服务预测差异可改变恢复状态。另用 4 阶段小场景验证 CP-SAT 与三种既有模型均真实调用共享运动接口并完成，PETS 与结构化网络调用分别为 93 与 87 次。此检查证明所测接口、分支隔离和已覆盖状态的运动规则一致，**不证明**世界模型的全部服务状态或任意新场景的多步预测已准确。

## 可复现与限制

从本 PR 工作目录，在 Linux、Python 3.10、C++17/CMake 环境（依赖版本见 `requirements-paper-reuse.lock`）执行：

```bash
python -m pip install 'uv==0.13.5'
uv pip install --system --index-strategy unsafe-best-match -r requirements-paper-reuse.lock
bash tools/pibt_motion/prepare_upstream.sh /tmp/wm-pibt-upstream
bash tools/lacam3_recovery/prepare_upstream.sh /tmp/wm-lacam-upstream
python -m tools.pibt_motion.prepare_sources --output /tmp/wm-hospital-sources
export WM_PIBT_LIBRARY=/tmp/wm-pibt-upstream/bridge/libwm_pibt_bridge.so
export WM_LACAM3_WORKER=/tmp/wm-lacam-upstream/bridge/wm_lacam3_worker
export WM_HOSPITAL_SOURCES=/tmp/wm-hospital-sources
python -m unittest discover -s experiments/lacam3_recovery/tests -v
bash tools/lacam3_recovery/run_acceptance.sh "$WM_LACAM3_WORKER" "$WM_PIBT_LIBRARY" "$WM_HOSPITAL_SOURCES" /tmp/wm-lacam-acceptance
```

上述目录必须不存在或为空，脚本拒绝覆盖。验收运行两遍，逐字段核对结果并排除实际耗时、CPU 和 RSS 的自然波动，同时校验原、PIBT 两后端与 PR #13 归档的 44 条历史运行的完整轨迹、事件、任务结果一致；最后再独立执行资源采样复跑。完整自动化还运行既有测试：[CPU 工作流](../.github/workflows/lacam3-recovery.yml)。本地共 165 项 Python 测试及上游 LaCAM3 6 项原生测试通过；实际 GitHub Actions 状态以 PR 的检查记录为准。

站点角色、容量、机器人初始位置、任务及服务时间是仿真假设；公开地图不等于真实实验室部署。当前适配不解决有向图完整联合规划、锁定资源使目标不可达、物理机器人连续碰撞检测、动态人员避障、SLAM、导航控制、设备通信、在线任务异常恢复或通信故障。超过 500 ms、冲突目标无法构造合法临时 MAPF 目标时均保留安全回退与失败记录，不保证最终活性。现有普通地图集规模有限，未来应在不改变交通规则的真实布局与更长运行上继续验证。
